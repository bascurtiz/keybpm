## Mix it! page: version + build stamp chip next to BETA

User wanted a version visible next to the BETA chip on `/mixit` so they can confirm the latest build is actually live.

**Discovery:** the plumbing already existed but was unused. `vite.config.ts` already had:

```ts
define: {
  __APP_VERSION__: JSON.stringify(pkg.version),   // from package.json
  __BUILD_DATE__: JSON.stringify(new Date().toISOString()),
}
```

Nothing in `src/` consumed either constant, and there were no ambient type declarations for them.

**Changes:**
1. `src/vite-env.d.ts` — added `declare const __APP_VERSION__: string` and `declare const __BUILD_DATE__: string`.
2. `src/pages/MixIt.tsx` — added a module-level `BUILD_STAMP` helper that formats `__BUILD_DATE__` as `YYYY-MM-DD HH:mm UTC`, plus a second chip after the BETA chip rendering `v{__APP_VERSION__} · {BUILD_STAMP}`, with the raw ISO in the `title`.

**Why UTC, deliberately:** `__BUILD_DATE__` is a build-time constant. Formatting it with the viewer's local timezone would render a different string for every visitor, which defeats the purpose of a deploy fingerprint. UTC is identical for everyone.

**Verified:** `tsc --noEmit` clean; `npx vite build` succeeds and the bundle contains `"1.0.1"` and the ISO build date, plus the chip markup (`title:"Build: 2026-10-15T22:36:38.840Z",children:["v",...]`).

**Caveat to remember:** the version comes from `package.json` (`1.0.1`) and only changes when bumped — `npm version patch|minor|major` works with no extra script. The build timestamp changes on every build, so it alone is enough to detect a fresh deploy even if the version wasn't bumped.

## Follow-up: version now auto-derived from git

User asked for it to be automatic rather than manually bumped.

`vite.config.ts` now derives the version at build time via a small `git()` helper (`execSync`, wrapped in try/catch so a missing git binary or a non-repo build can never break the build):

- `git rev-list --count HEAD` → commit count
- `git rev-parse --short HEAD` → short SHA
- `git rev-parse --abbrev-ref HEAD` → branch
- `git status --porcelain --untracked-files=no` → dirty flag

`--untracked-files=no` is deliberate: otherwise `dist/` and other build artifacts would mark every single build dirty.

Version shape: `${pkg.version}+${commits}.${sha}` plus `.dirty` when tracked files were modified, e.g. `1.0.1+123.f327a62.dirty`. Valid semver build metadata. Falls back to the bare package version when git is unavailable.

New build-time constants (all declared in `src/vite-env.d.ts`): `__GIT_SHA__`, `__GIT_BRANCH__`, `__GIT_DIRTY__`, alongside the existing `__APP_VERSION__` / `__BUILD_DATE__`.

`MixIt.tsx` chip now renders `v{__APP_VERSION__} · {BUILD_STAMP}` and the tooltip lists version / build ISO / commit / branch, plus a warning line when built dirty. **The chip turns amber (`bg-warn/10 text-warn border-warn/30`) when `__GIT_DIRTY__`** so an uncommitted build is obvious at a glance — worth remembering, since a dirty build doesn't correspond to any commit.

Verified against the real repo: injected `Version: 1.0.1+123.f327a62.dirty`, `Commit:  f327a62`, `Branch:  main` all present in the shipped bundle and matching `git rev-parse` output. `npm run build` (tsc -b + vite build) passes.

## SCR cutter: replaced the synthesis with real sample playback

Earlier the same day the SCR button (Mix it! FX strip) was a *synthesised* cutter — an RAF loop driving `scratchMove()` + `setCrossfadeGain()` over 8 sixteenth-note cells, reverse-stroking the deck's own vinyl at `CUT_RATE = -1.6` with the crossfader held at `CUT_GAIN = 0.45`. It was reverse-engineered from `D:\Music\keybpm-test\cutter.wav` and it never really satisfied the user.

**Final approach — just play the recording.** The user supplied `Phat Drum 1.wav` (a drum loop) and asked for it to be triggered at the deck's tempo instead.

**Asset:** `D:\Music\keybpm-test\Phat Drum 1.wav` → `public/sounds/cutter.audio`. Measured: 190,172 bytes, RIFF/WAVE 16-bit **stereo 44.1 kHz**, 46,186 frames = **1.0473 s**, peak 0.595, RMS −15.9 dBFS, loud attack → quiet tail (a decaying loop, not a sustained one). At the user's stated 120 BPM, 2 beats = 1.0 s, so the loop is ~2 beats — the reading is consistent, and the "2 beats vs 4 beats" ambiguity from the earlier analysis is settled by trusting the user's stated tempo.

**Convention:** `.audio` files in `public/sounds/` are plain RIFF/WAVE with a renamed extension, fetched + `decodeAudioData`'d — same as the existing `guitar-C*.audio` / `piano-C*.audio` (see `src/lib/audioEngine.ts`). Vite copies `public/` verbatim, so no import plumbing is needed.

**`src/lib/dj/deck-engine.ts`:**
- New module constants: `CUTTER_SAMPLE_BPM = 120`, `CUTTER_LEVEL = 1`, `CUTTER_MIN_RATE = 0.5`, `CUTTER_MAX_RATE = 2`, `CUTTER_RETRIGGER_FADE_S = 0.008`.
- New fields: `cutterGain` (readonly GainNode), `cutterBuffer`, `cutterLoad` (in-flight promise), `cutterVoice` (`{source, gain}`), `_masterBpm = 128`.
- **Where the sample enters the graph:** `cutterGain.connect(this.eqLow)` — i.e. ahead of the EQ but *after* `autoGain`/`trim`. Deliberate: the chop should be shaped by the channel's EQ / filter / fader / crossfader (and hit the echo/reverb/flanger sends, which tap `this.filter`) exactly like the track, but must **not** be re-normalised by `autoGain` against whatever track is loaded. Node is built in the constructor so `triggerCutter` never mutates the graph mid-playback.
- `triggerCutter()` rewritten: `createBufferSource()` → per-trigger gain (`CUTTER_LEVEL`) → `cutterGain` → `start()`. Re-press fades the outgoing chop over `CUTTER_RETRIGGER_FADE_S` and `stop()`s it (a hard stop mid-waveform clicks); `onended` tears the nodes down.
- `cutterPlaybackRate()`: `effectiveBpm / CUTTER_SAMPLE_BPM`, clamped. **The deck's own tempo wins**; `_masterBpm` is only the fallback for a deck with no track.
- `loadCutterSample()`: fetch + decode once per deck, cached on the instance; a failed load clears `cutterLoad` so a later press retries instead of caching the failure.

**No sample-rate correction needed.** `playbackRate = 1.0` plays the buffer at its own 44.1 kHz whatever the context runs at — the resampler lives inside `AudioBufferSourceNode`. The earlier worry about 44.1 vs 48 kHz was unfounded for this path.

**Master Tempo plumbing (new).** `AudioEngine.masterBpm` (the top-bar "Master Tempo (BPM)" field, default 128) was not visible to `DeckEngine` at all. Added `DeckEngine.masterBpm` getter + `setMasterBpm(bpm)`, pushed from `AudioEngine` in the constructor and in `setMasterBpm()` (before the `syncDecks` branch, so it is mirrored whether or not the pitch faders are re-driven).

**Call site:** `TraktorMixer.tsx` `triggerCutter` wrapper was unchanged (still routes by FX assign A / B / MST, skipping decks with no track). Only the button `title` was updated.

**Verified:** `tsc --noEmit` clean; `npm run build` succeeds; `dist/sounds/cutter.audio` present (190,172 bytes) and the bundle contains the literal `sounds/cutter.audio`; served from `vite preview` with HTTP 200 and intact RIFF magic. Build stamp showed `1.0.1+124.df24fb8.dirty`.

**Note:** `triggerCutter` is now polyphony-free by design — one chop at a time, retriggered. The old `scratchBegin`/`scratchMove`/`scratchEnd` + `setCrossfadeGain` path is still used by the jog wheel, `triggerBrake` and `triggerBackspin`; the cutter no longer touches the crossfader at all (which also removes the old risk of leaving the xfade stuck at `CUT_GAIN`).

## SCR cutter: beatgrid quantise + automatic level

Two follow-ups the user asked for. Both are in `src/lib/dj/deck-engine.ts`.

### The level bug, and what actually caused it

The user reported the chop was loud enough on `Fish Go Deep … (Dennis Ferrer Remix).mp3` but too quiet on `Catscan - Smeerpijp.flac`. Measured with the **real** `autogain.ts` over PCM decoded from the actual files:

| track | 90th-pct RMS | `computeAutoGain` | track after gain |
|---|---|---|---|
| Catscan – Smeerpijp | 0.7140 (−2.93 dBFS) | **0.400 — clamped at `MIN_GAIN`** | 0.2856 |
| Fish Go Deep | 0.2917 (−10.70 dBFS) | 0.754 | 0.2199 |
| Phat Drum 1 (the chop) | — | — | 0.1593 (plain RMS) |

Catscan is a brickwalled master so loud that the auto-gain hits its `MIN_GAIN = 0.4` floor (it wanted 0.308). Because the chop enters the graph **after** `autoGain`, it was a fixed −15.96 dBFS absolute on every track: **−2.80 dB** under the track on three of the four test tracks but **−5.07 dB** under Catscan. That 2.27 dB inconsistency is the whole complaint.

**The fix is NOT to apply the track's gain to the chop** — that runs the wrong way (it would have dropped the chop to −11 dB under Catscan). The chop is a *different recording with its own loudness*, so it has to normalise itself to the level the track lands at:

```
cutterLevel = clamp( (track.loudness * track.gain) * CUTTER_TRACK_LEVEL / chopLoudness )
```

`track.loudness * track.gain` is exactly what the deck emits, so this holds even when the auto-gain is clamped. Result: a constant **0.00 dB** chop-vs-track on all four tracks (gain 1.381 on three, 1.793 on Catscan).

- `autogain.ts`: `TARGET_RMS` now exported; `computeAutoGain` refactored onto a new exported `measureLoudness(buffer)` (same maths, returns `null` when <4 blocks or silent). New `measureLevel(buffer)` = whole-buffer RMS, for sources too short for a percentile — **the chop loop is only 1.047 s, so `measureLoudness` returns `null` for it** (2 blocks < 4). Measured 400 ms blocks read 0.172 / 0.150 vs an overall RMS of 0.159, so the plain RMS is the honest number for a loop that short.
- `types.ts`: `Track.loudness?: number` (raw loudness before `gain`). `track-analyzer.ts` records it.
- Constants: `CUTTER_TRACK_LEVEL = 1` (**the one knob** — 1 = chop at the track's RMS), `CUTTER_LEVEL_FALLBACK = 1.4`, `CUTTER_GAIN_MIN/MAX = 0.25 / 4`.

### Quantise

User's chosen semantics: **never start off-grid — always wait for the next beat**; **QUANT off means instant**. Implemented by handing `source.start()` the context time of the next beat, so it is sample accurate — deliberately *not* a `setTimeout`, which would drift with main-thread load. (The hot-cue quantiser uses a timer because it has to `seek()`; a one-shot buffer source does not.)

- `cutterQuantizeDelay()` returns 0 when QUANT is off, the deck is not playing, or there is no grid. Otherwise it waits for `beatTimeAt(grid, floor(beatIndexAt(grid,pos)) + 1)` — the **next beat's own time**, not one local beat length out. On a drifting grid `beatLengthAt` is a windowed *average*, which left a 1.28 ms error; using the real next beat made it 0.000000 ms.
- The wait is divided by `_rate`, or the chop lands late on a pitched deck.
- `cutterGraceSeconds()` = `CUTTER_QUANT_GRACE_S (0.035) + min(CUTTER_MAX_LATENCY_ALLOWANCE_S, ctx.outputLatency || ctx.baseLatency)`. The deck's position leads what is **heard** by the output latency (the worklet advances as it renders; the vinyl worklet does no latency compensation), so a press made in time with the music reads as `outputLatency` past the beat — without this a slow output path pushed that press a **whole beat late**. Capped at 80 ms so a nonsense driver reading can't swallow half a beat.
- `CutterVoice` gained `startAt`, so `retireCutterVoice()` knows whether to *cancel* (not yet sounded → `stop()` + disconnect) or *fade* (sounding). `cancelPendingCutter()` is wired into `pause()`, `seek()` (the single path every jump goes through — hot cues, beat jumps, CUE) and `loadTrack()` (which bypasses `pause()`).

### Verification

`tsc --noEmit` clean, `npm run build` clean. Harnesses live in `C:\Users\Ferdinand\AppData\Local\Temp\keybpm-verify\` and **read the constants out of `deck-engine.ts`** so they cannot drift, and **import the real bundled `autogain.ts` / `grid.ts`** rather than reimplementing them:

- `verify-quantize.mjs` — real grid helpers, 5 grid shapes × rates + latency cases. All deferred chops land with **0.000000 ms** error; the three "fire now" cases and the latency case behave.
- `cutter-level.html` — self-contained audition page (base64 FLAC excerpts, 2.9 MB) with an old-vs-new toggle and a live `CUTTER_TRACK_LEVEL` slider, so the constant can be picked by ear.

**Known trade-off, surfaced to the user:** `CUTTER_TRACK_LEVEL = 1` lifts the chop **+2.80 dB** on Fish Go Deep (the track they had called "loud enough") and **+5.07 dB** on Catscan. Level match was chosen because a real scratch *is* the track, and because +2.27 dB (anchoring on the old Fish Go Deep level) was judged too small to un-bury a chop under a brickwalled master. ## Auto-gain: actually equal loudness on both decks

User asked to "put autogain also on the 2 decks, so they are always equal loud on 100% volume slider".

**Auto-gain was already on both decks.** `DeckEngine` has had a per-deck `autoGain` GainNode since before this work, and *every* audio path goes through it — `keyLockDryGain → autoGain` and `keyLockWetGain → autoGain` in the constructor, then `autoGain → trim → EQ → filter → fader → analyser → xfade`. `loadTrack` applies it at line ~1200 via `setTargetAtTime(track.gain || 1, …)`. So the real problem was not a missing stage — it was that the stage could not finish its job.

**Two things stopped it equalising:**

1. **`MIN_GAIN = 0.4` clamped loud masters.** `computeAutoGain` returns `TARGET_RMS / loudness`, so `loudness * gain === TARGET_RMS` exactly — *unless a clamp bites*. Catscan's 90th-pct RMS is 0.7140, needing a gain of 0.308, but the floor stopped it at 0.400, leaving it at 0.2856 instead of 0.2200 — **2.27 dB louder than every other track at the same fader position**. Relaxed to `MIN_GAIN = 0.1` (attenuation is free of risk). `MAX_GAIN` 3 → 6, kept much tighter than the floor because boosting a quiet recording boosts its noise floor with it.
2. **`demo-tracks.ts` hardcoded `gain: 1`.** The synthesised demo tracks bypassed auto-gain entirely, so they matched neither each other nor anything else. Now `computeAutoGain(buffer)`. The other two load paths were already correct: `track-analyzer.ts` (`gain = computeAutoGain(buffer)`, used by `MixIt.tsx:93/95`) and the YouTube-transfer path (`MixIt.tsx:153`).

**Verified** (`verify-equal-loud.mjs`, real bundled `autogain.ts` over PCM from the actual files):

| track | loudness | gain | level | old gain | old level | old drift |
|---|---|---|---|---|---|---|
| Catscan – Smeerpijp | 0.7140 | **0.308** | 0.22000 | 0.400 | 0.28559 | **+2.27 dB** |
| Fish Go Deep | 0.2917 | 0.754 | 0.22000 | 0.754 | 0.22000 | 0 |
| Angerfist – Freddy | 0.5454 | 0.403 | 0.22000 | 0.403 | 0.22000 | 0 |
| Nightcrawlers | 0.1335 | 1.648 | 0.22000 | 1.648 | 0.22000 | 0 |

Spread after: **0.0000 dB** (was 2.27 dB).

**Side effect on the cutter:** because every track now lands on `TARGET_RMS`, `cutterLevel()` collapses to the constant `0.2200 / 0.15931 = 1.381` on every track. The formula is kept — it is still the correct expression of intent and still covers the `CUTTER_LEVEL_FALLBACK` path — but the chop gain is no longer track-dependent in practice. The audition page's baked-in Catscan gain was updated 0.400 → 0.308.

## KEY label now toggles keylock

User asked for the `KEY` text above the key knob to be clickable to "turn it off". Via two clarifying questions they settled on: **keylock only** (not the key-sync mirror, and not both).

**Why it needed a question:** the label was ambiguous. In `TraktorDeck.tsx` the `KEY` span sat above the key-transpose `Knob` and was coloured by `isKeySynced` — so it *looked* like a key-sync control — while `DeckEngine` separately has `keyLock` (`_keyLock = true` by default, `setKeyLock` / `toggleKeyLock`) which had **no UI anywhere in the app**. The two readings produce different UI (what the label's amber means) so it was worth pinning down rather than guessing.

**Change** (`TraktorDeck.tsx`, the "Key Transpose Section"): the `KEY` `<span>` became a `<button type="button">` wired to `deck.toggleKeyLock()`. `disabled={!deck.track}` — deliberately *not* requiring the other deck, since keylock is per-deck, unlike the `SYNC` button below it which still calls `handleKeySync` (`isKeySynced` / `handleKeySync` both remain in use by SYNC, so no dead code).

**Colour meaning flipped:** amber now tracks `deck.keyLock`, not `isKeySynced`. Keylock defaults **on**, so amber is the resting state and grey means keylock is off. Hover mirrors the SYNC button's pattern (`hover:text-amber-300` when lit, `hover:text-white` + `disabled:opacity-30` when not).

**Engine semantics confirmed by reading, worth remembering:**
- `updateKeyLockRouting()` computes `needsKeyLock = this._keyLock || this._keyShift !== 0` (line ~827), so **keylock off changes nothing while a key shift is dialled in** — the stretch engine stays engaged. The button's tooltip says so.
- `pitch = (this._keyLock ? 1 / effectiveRate : 1) * Math.pow(2, this._keyShift / 12)` (line ~834) — so keylock off means the pitch fader moves the key, i.e. vinyl behaviour. That is the intended effect.
- Routing is `active ? wetGain 1 / dryGain 0 : wetGain 0 / dryGain 1` (lines ~853-859), so off genuinely switches to the dry path.
- Both keylock engines are fed the vinyl worklet's already-resampled output, so keylock is a pure pitch shift of `1/rate` plus the key shift.

**Verified:** `tsc --noEmit` and `npm run build` clean; bundle contains both tooltip strings and two `toggleKeyLock` occurrences (definition + call site).

**Note:** `src/components/dj/DeckControls.tsx` is dead code — never imported anywhere, and it carries its own duplicate `KEY` label (line ~223) plus a copy of the key-sync logic. Left untouched, but it will drift from `TraktorDeck` and is a candidate for deletion.
