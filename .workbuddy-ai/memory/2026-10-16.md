## Follow-up: version now auto-derived from git

User asked for it to be automatic rather than manually bumped.

`vite.config.ts` now derives the version at build time via a small `git()` helper (`execSync`, wrapped in try/catch so a missing git binary or a non-repo build can never break the build):

- `git rev-list --count HEAD` → commit count
- `git rev-parse --short HEAD` → short SHA
- `git rev-parse --abbrev-ref HEAD` → branch
- `git status --porcelain --untracked-files=no` → dirty flag

`--untracked-files=no` is deliberate: otherwise `dist/` and other build artifacts would mark every single build dirty.

Version shape: `${pkg.version}+${commits}.${sha}` plus `.dirty` when tracked files were modified, e.g. `1.0.1+123.f327a62.dirty`. Valid semver build metadata. Falls back to the bare package version when git is unavailable.

New build-time constants (all declared in `src/vite-env.d.ts`): `__GIT_SHA__`, `__GIT_BRANCH__`, `__GIT_DIRTY__`, alongside the existing `__APP_VERSION__` / `__BUILD_DATE__`.

`MixIt.tsx` chip now renders `v{__APP_VERSION__} · {BUILD_STAMP}` and the tooltip lists version / build ISO / commit / branch, plus a warning line when built dirty. **The chip turns amber (`bg-warn/10 text-warn border-warn/30`) when `__GIT_DIRTY__`** so an uncommitted build is obvious at a glance — worth remembering, since a dirty build doesn't correspond to any commit.

Verified against the real repo: injected `Version: 1.0.1+123.f327a62.dirty`, `Commit:  f327a62`, `Branch:  main` all present in the shipped bundle and matching `git rev-parse` output. `npm run build` (tsc -b + vite build) passes.

## SCR cutter: beatgrid quantise + automatic level

Two follow-ups the user asked for. Both are in `src/lib/dj/deck-engine.ts`.

### The level bug, and what actually caused it

The user reported the chop was loud enough on `Fish Go Deep … (Dennis Ferrer Remix).mp3` but too quiet on `Catscan - Smeerpijp.flac`. Measured with the **real** `autogain.ts` over PCM decoded from the actual files:

| track | 90th-pct RMS | `computeAutoGain` | track after gain |
|---|---|---|---|
| Catscan – Smeerpijp | 0.7140 (−2.93 dBFS) | **0.400 — clamped at `MIN_GAIN`** | 0.2856 |
| Fish Go Deep | 0.2917 (−10.70 dBFS) | 0.754 | 0.2199 |
| Phat Drum 1 (the chop) | — | — | 0.1593 (plain RMS) |

Catscan is a brickwalled master so loud that the auto-gain hits its `MIN_GAIN = 0.4` floor (it wanted 0.308). Because the chop enters the graph **after** `autoGain`, it was a fixed −15.96 dBFS absolute on every track: **−2.80 dB** under the track on three of the four test tracks but **−5.07 dB** under Catscan. That 2.27 dB inconsistency is the whole complaint.

**The fix is NOT to apply the track's gain to the chop** — that runs the wrong way (it would have dropped the chop to −11 dB under Catscan). The chop is a *different recording with its own loudness*, so it has to normalise itself to the level the track lands at:

```
cutterLevel = clamp( (track.loudness * track.gain) * CUTTER_TRACK_LEVEL / chopLoudness )
```

`track.loudness * track.gain` is exactly what the deck emits, so this holds even when the auto-gain is clamped. Result: a constant **0.00 dB** chop-vs-track on all four tracks (gain 1.381 on three, 1.793 on Catscan).

- `autogain.ts`: `TARGET_RMS` now exported; `computeAutoGain` refactored onto a new exported `measureLoudness(buffer)` (same maths, returns `null` when <4 blocks or silent). New `measureLevel(buffer)` = whole-buffer RMS, for sources too short for a percentile — **the chop loop is only 1.047 s, so `measureLoudness` returns `null` for it** (2 blocks < 4). Measured 400 ms blocks read 0.172 / 0.150 vs an overall RMS of 0.159, so the plain RMS is the honest number for a loop that short.
- `types.ts`: `Track.loudness?: number` (raw loudness before `gain`). `track-analyzer.ts` records it.
- Constants: `CUTTER_TRACK_LEVEL = 1` (**the one knob** — 1 = chop at the track's RMS), `CUTTER_LEVEL_FALLBACK = 1.4`, `CUTTER_GAIN_MIN/MAX = 0.25 / 4`.

### Quantise

User's chosen semantics: **never start off-grid — always wait for the next beat**; **QUANT off means instant**. Implemented by handing `source.start()` the context time of the next beat, so it is sample accurate — deliberately *not* a `setTimeout`, which would drift with main-thread load. (The hot-cue quantiser uses a timer because it has to `seek()`; a one-shot buffer source does not.)

- `cutterQuantizeDelay()` returns 0 when QUANT is off, the deck is not playing, or there is no grid. Otherwise it waits for `beatTimeAt(grid, floor(beatIndexAt(grid,pos)) + 1)` — the **next beat's own time**, not one local beat length out. On a drifting grid `beatLengthAt` is a windowed *average*, which left a 1.28 ms error; using the real next beat made it 0.000000 ms.
- The wait is divided by `_rate`, or the chop lands late on a pitched deck.
- `cutterGraceSeconds()` = `CUTTER_QUANT_GRACE_S (0.035) + min(CUTTER_MAX_LATENCY_ALLOWANCE_S, ctx.outputLatency || ctx.baseLatency)`. The deck's position leads what is **heard** by the output latency (the worklet advances as it renders; the vinyl worklet does no latency compensation), so a press made in time with the music reads as `outputLatency` past the beat — without this a slow output path pushed that press a **whole beat late**. Capped at 80 ms so a nonsense driver reading can't swallow half a beat.
- `CutterVoice` gained `startAt`, so `retireCutterVoice()` knows whether to *cancel* (not yet sounded → `stop()` + disconnect) or *fade* (sounding). `cancelPendingCutter()` is wired into `pause()`, `seek()` (the single path every jump goes through — hot cues, beat jumps, CUE) and `loadTrack()` (which bypasses `pause()`).

## Auto-gain: actually equal loudness on both decks

User asked to "put autogain also on the 2 decks, so they are always equal loud on 100% volume slider".

**Auto-gain was already on both decks.** `DeckEngine` has had a per-deck `autoGain` GainNode since before this work, and *every* audio path goes through it — `keyLockDryGain → autoGain` and `keyLockWetGain → autoGain` in the constructor, then `autoGain → trim → EQ → filter → fader → analyser → xfade`. `loadTrack` applies it at line ~1200 via `setTargetAtTime(track.gain || 1, …)`. So the real problem was not a missing stage — it was that the stage could not finish its job.

**Two things stopped it equalising:**

1. **`MIN_GAIN = 0.4` clamped loud masters.** `computeAutoGain` returns `TARGET_RMS / loudness`, so `loudness * gain === TARGET_RMS` exactly — *unless a clamp bites*. Catscan's 90th-pct RMS is 0.7140, needing a gain of 0.308, but the floor stopped it at 0.400, leaving it at 0.2856 instead of 0.2200 — **2.27 dB louder than every other track at the same fader position**. Relaxed to `MIN_GAIN = 0.1` (attenuation is free of risk). `MAX_GAIN` 3 → 6, kept much tighter than the floor because boosting a quiet recording boosts its noise floor with it.
2. **`demo-tracks.ts` hardcoded `gain: 1`.** The synthesised demo tracks bypassed auto-gain entirely, so they matched neither each other nor anything else. Now `computeAutoGain(buffer)`. The other two load paths were already correct: `track-analyzer.ts` (`gain = computeAutoGain(buffer)`, used by `MixIt.tsx:93/95`) and the YouTube-transfer path (`MixIt.tsx:153`).

**Verified** (`verify-equal-loud.mjs`, real bundled `autogain.ts` over PCM from the actual files):

| track | loudness | gain | level | old gain | old level | old drift |
|---|---|---|---|---|---|---|
| Catscan – Smeerpijp | 0.7140 | **0.308** | 0.22000 | 0.400 | 0.28559 | **+2.27 dB** |
| Fish Go Deep | 0.2917 | 0.754 | 0.22000 | 0.754 | 0.22000 | 0 |
| Angerfist – Freddy | 0.5454 | 0.403 | 0.22000 | 0.403 | 0.22000 | 0 |
| Nightcrawlers | 0.1335 | 1.648 | 0.22000 | 1.648 | 0.22000 | 0 |

Spread after: **0.0000 dB** (was 2.27 dB).

**Side effect on the cutter:** because every track now lands on `TARGET_RMS`, `cutterLevel()` collapses to the constant `0.2200 / 0.15931 = 1.381` on every track. The formula is kept — it is still the correct expression of intent and still covers the `CUTTER_LEVEL_FALLBACK` path — but the chop gain is no longer track-dependent in practice. The audition page's baked-in Catscan gain was updated 0.400 → 0.308.

## Keylock wobbled at original BPM — root-caused and fixed

User: *"the moment we have key on, the tracks seems to wobble. even on original bpm."* Real bug, present since forever — keylock defaulted on with no UI, so it was only A/B-able after the `KEY` button landed.

**Root cause: the WSOLA seek re-times windows when there is nothing to re-time.**

Both keylock engines (`soundtouch`, `rubberband`) are WSOLA-family time-stretchers. Their overlap-add stage picks a per-window offset by cross-correlation (`Stretch.seekBestOverlapPosition`) to find the best alignment with the previous window. At a real ratio that is the point of the algorithm; at unity it is pure damage.

The subtlety that took the longest to pin down: **a *constant* non-zero offset is harmless** — consecutive windows still agree, so the crossfade joins a sample to itself, and the output is an exact (merely delayed) copy. Only a *changing* offset tears the timeline, because the crossfade then joins two different points in the source. The 8 ms overlap crossfade smears each tear into a warble. Algebraically: window `k` at input `P_k` with offset `o_k` reconstructs exactly iff `o_{k+1} == o_k`.

**Measurement** (harness: `C:/Users/Ferdinand/AppData/Local/Temp/keybpm-verify/keylock-wobble.mjs`). Loads the real `public/soundtouch-processor.js` in a Node VM — it is a flat script with top-level `var` classes, so `SoundTouch`/`Stretch` land on the context global; only `AudioWorkletProcessor`, `registerProcessor` and `sampleRate` need stubbing. Feeds PCM in 128-frame blocks exactly as `processCore` does, and wraps `Stretch.prototype.seekBestOverlapPosition` to read the chosen offsets directly.

| track (12 s, centred fader) | windows | re-timings | max jump | timeline warp |
|---|---|---|---|---|
| Catscan – Smeerpijp | 88 | 15 | 21.7 ms | 22.5 ms |
| Fish Go Deep (D Ferrer Rmx) | 88 | 31 | 21.6 ms | 23.0 ms |
| Angerfist – Freddy | 88 | 0 | 0.0 ms | 0.0 ms |
| Nightcrawlers – Push The Feeling | 88 | 26 | 18.1 ms | 23.0 ms |

Forcing the seek to 0, or freezing it at its first offset, drops re-timings to **0**. Control on broadband noise: the seek finds nothing to lock onto, stays at 0, and the pipe is **bit-exact** (residual 0.00%, level ratio 1.0000, drift 0.04 samples). So the artefact is **material-dependent** — correlated/tonal music gives the seek something to lock onto; noise does not. Angerfist (purely percussive) was the one track that stayed clean.

**Fix.** New `src/lib/dj/keylock-transform.ts` — pure, dependency-free, exports `keyLockTransform(rate, nudgeFactor, pllCorrection, keyLock, keyShiftSemitones) → { pitch, ratePitch, identity }`. `identity` is `|1200·log2(pitch)| < KEYLOCK_UNITY_CENTS` (1 cent; the faders step 0.05% = 0.87 cents, so this covers the centre detent plus the step either side). `deck-engine.ts` folds `!identity` into the existing `active` gate, so an identity transform plays the **dry** path. The engine keeps running and keeps being fed, and the SoundTouch params are still written, so the wet path is primed for the moment the fader leaves the detent.

It is kept as a separate module so the routing decision can be exercised without an AudioContext — `deck-engine.ts` imports browser-only worklet packages and cannot be bundled for Node.

`ratePitch` is returned alongside `pitch` because SoundTouch folds the key shift in itself (`_pipe.pitch = pitch * 2^(pitchSemitones/12) / playbackRate`) and must be given the **rate part only** — passing `pitch` there would apply the shift twice. Verified as an invariant over 154 combinations.

**Verified:** `tsc --noEmit` clean; `npm run build` clean; bundle contains the new tooltip text and the `1200*Math.log2(...)` identity test; existing suite still green (`verify.mjs`, `verify-quantize.mjs`, `verify-equal-loud.mjs`, `check-page.mjs`); 16/16 routing cases pass (`verify-keylock-routing.mjs`, bundled from the repo with its own esbuild).

**Harness traps worth remembering** (each cost a wrong answer first):
- Correlating *music* for a pipeline delay is unreliable — a repetitive track correlates just as well one beat off, which silently corrupts every residual/level figure. Use broadband noise for delay-dependent claims, or read the seek offsets directly.
- The pipeline delay is ~5600 samples at 44.1 kHz; a ±4096 search truncates and locks onto a spurious peak. Hence `DELAY_SEARCH_SPAN = 8192` plus a throw if the result lands on the boundary.
- Compare output level against the input at the *aligned* position, not the same index, or you measure the music's own dynamics.

**Known remaining limitation (not addressed):** at ratios away from unity the WSOLA artefacts are still there — measured 2.6–5.3 dB of level modulation at 1.06×. That is inherent to SoundTouch on percussive material, and is what the `rubberband` engine exists for (`setKeyLockEngine('rubberband')`). SoundTouch stays the default because its pitch is an AudioParam, so continuous pitch changes ramp instead of restarting the stretch.

**A/B audio left for the user** in `outputs/keylock-ab/` (gitignored): `keylock-1-before.wav` (keylock on as shipped — the wobble), `keylock-2-seek-off.wav` (same pipe, seek neutralised — clean), `keylock-3-after.wav` (what the deck plays now), all trimmed to the same track instant and level-matched, plus `measurements.txt`.

## Stacked lanes did not line up between decks — two independent causes, both fixed

Reported: *"shouldnt they align? coz right now they are audible, but visual they are not"*, then the decisive
clue *"it only happens when i put key lock on, one either one or both. when both have key lock off, they do
align."* Two separate bugs produced the same symptom.

**Cause 1 — the lanes were drawn on each track's own source-time axis.** `renderDeckLane` used a single
`secPerPx = windowSeconds / w` for both decks. A synced pair runs at the same *playback* tempo but different
*rates*, so on a source-time axis the two grids have different widths — identical only at the playhead and
diverging with distance. Measured off the screenshot: deck A 363.5 px/bar (rate 1.000) vs deck B 355.2 px
(rate 0.976), 2.3 % apart, while both reported 123.04 BPM. Fixed with `src/lib/dj/waveform-timebase.ts`:
`secPerPx_source = (windowSeconds / w) * rate`, `tStart_source = pos - (windowSeconds / 2) * rate`. Worst
grid mismatch across the lane 13.3 px -> 0.00 px.

**Cause 2 — keylock latency, which is why it was keylock-conditional.** A deck reports its position from the
vinyl worklet, which sits *before* the keylock engine, so with the wet path live the sound runs ~133 ms behind
the reported position. The lane was centred on that read head, so the keylocked deck's grid was drawn a
quarter of a beat off. That is 0.133 s * (1120 px / 6 s) = **24.8 px** on this zoom; the screenshot measured
**23.5 px**, and the *direction* also matches (a dry deck's grid sits right of a keylocked one's, and A sat
~25 px right of B — so B was the deck holding the key). Fixed by centring the lane on
`DeckEngine.audiblePosition` instead of `position`.

Derivation, which is why the fix is exact rather than approximate. For a deck at rate `v`, read head `r`,
latency `L`, audible `a = r - L*v`, and a beat `phi` source seconds after `a`:

```
centre = a  ->  x - W/2 = (phi / v) * W/WINDOW
centre = r  ->  x - W/2 = (phi / v - L) * W/WINDOW
```

The first form depends only on `phi / v`, the offset to the beat in *playback* time — which two audibly-synced
decks share by definition. So the audible-centred lane makes them coincide for **any** rates and **any**
latencies, while the read-head one splits them by exactly `(L_A - L_B) * W/WINDOW`. That also explains the
"both keylocked" half of the report: with equal latencies the old rule was already fine, so that case must
have been cause 1.

**Also moved to `audiblePosition`:** the FLUX/slip ghost needles (`fluxPosition - position` -> `- audiblePosition`;
both needles share the lane's centre, so they must share its reference) and the 4-beat bar counter in
`TopBar.tsx` (window 0.04 beat vs 0.27 beat of error — the light would flip a quarter beat early).

**Deliberately left on the read head:** `MiniWaveform` progress (`position / duration`), the `m:ss` clocks in
`TopBar` and `TraktorMiddleStrip`, and `handlePointerDown`'s drag anchor. 133 ms is below the resolution of a
track clock, and switching would make the clock tick *backwards* when keylock engages; seeking genuinely wants
the read head. Judgement call, not an oversight.

**Refactor:** the latency arithmetic now lives in `keylock-transform.ts` (`keyLockLatencySeconds`,
`audiblePosition`, `ST_KEYLOCK_LATENCY_SECONDS = 0.133`, `RB_KEYLOCK_LATENCY_SECONDS = 0.15`) so the harness
exercises the real functions instead of a copy. `KeyLockEngine` moved there too and is re-exported from

**Open, deliberately not changed — the audio, not the display.** `alignPhaseTo` bar-aligns *read heads*
(`barPhaseAt(grid, this.position)`), and nothing compensates for keylock latency, so a synced pair where
exactly one deck holds the key is genuinely ~133 ms apart in the audio. The lane fix shows that honestly
rather than hiding it. Compensating it is a change to sync; not made, because the user reports the audio

## Rubber Band realtime latency measured — the borrowed 0.15 s was 40% too high

`RB_KEYLOCK_LATENCY_SECONDS = 0.15` was never measured for the realtime path; it was copied
from `rubberband-offline.ts`, which is the offline push/pull path *with a flush at the end*.
New harness `measure-rb-latency.mjs` loads `public/rubberband-processor.js` in a Node VM and
feeds it the way an AudioWorkletNode does.

**How to load that processor in Node** (it is a webpack bundle, unlike the SoundTouch one):
it embeds its WASM as a `data:application/octet-stream;base64,` URL and only calls `fetch`
when `typeof fetch === "function"`. So the VM context must simply **not define `fetch`** and
the base64 path is taken — no wasm file needed. Stub `sampleRate`, `console`,
`AudioWorkletProcessor` (with a `port`), `registerProcessor` (capture the class),
`TextDecoder`, `TextEncoder`, `WebAssembly`, `setTimeout`. The processor takes settings as
JSON arrays over `port.onmessage` (`['pitch'|'tempo'|'quality'|'close', value]`), and
`getApi` is **lazy** — it reads `this.pitch` / `this.tempo` / `this.highQuality` when the
first `process` call builds the kernel, so the messages must be sent *before* the loop.
WASM instantiation is async, so `await setImmediate` between the early blocks.

**Result — measured at a centred fader, tempo 1, highQuality true:**

| sample rate | delay (samples) | delay (ms) | correlation peak |
|---|---|---|---|
| 44100 | 4096 | 92.9 | 0.998 |
| 48000 | 4096 | 85.3 | 0.997 |

Exactly 4096 samples at *both* rates — so Rubber Band's realtime buffer is a fixed
**sample** count, where SoundTouch's WSOLA is a fixed **time** (5864 @ 44.1k / 6369 @ 48k,
both ≈133 ms). Hence `RB_KEYLOCK_LATENCY_SAMPLES = 4096` and `keyLockLatencySeconds` now
takes a `sampleRate` (SoundTouch ignores it). At ratios away from unity the correlation
peaks collapse to ~0.045 — meaningless, same trap as before, so only the centred row is
evidence.

**Sync now compensates.** `alignPhaseTo` compared `this.position` / `other.position`, i.e.
read heads, so a synced pair where exactly one deck held the key was genuinely ~133 ms apart
in the audio. It now compares `audiblePosition` on both sides (and evaluates `barLengthAt`
there too). Because the correction is a source-time shift and subtracting a constant latency
commutes with it, shifting the read head by `shift` moves the audible position by `shift`
as well. Both decks report zero latency when dry, so this is a no-op in the common case.

**Verified:** `tsc --noEmit` clean; `npm run build` clean; full `npm test` green (105 + 74 +

## SoundTouch vs Rubber Band — what the evidence actually supports

New harness `compare-keylock-engines.mjs`, built after two failed attempts (below). Both
engines fed exactly what the deck sends: SoundTouch `pipe.pitch = 1/rate`; Rubber Band
`setPitch(1/rate)`, `setTempo(1)`, `highQuality`. Steady signals only, because the artefact
is a *gain* artefact and on steady signals any output envelope movement **is** the artefact —
no output-vs-input alignment is needed at all.

Signals: `sine 1 kHz`, `saw 110 Hz + 8 harmonics`, `noise`. Metric: p5–p95 spread of the
10 ms RMS envelope, in dB. **The input row is the metric's floor** — 0.00 / 0.89 / 1.40 dB
respectively, from the window not aligning with the waveform period. Compare output against
input, never absolutely.

| signal | ratio | SoundTouch AM | RubberBand AM |
|---|---|---|---|
| sine | 1.00 | 0.00 | 0.00 |
| sine | 1.02 / 1.06 / 0.96 | 0.13 / 0.06 / 0.07 | 0.13 / 0.06 / 0.07 |
| saw | 1.00 | 0.95 (in 0.89) | 0.98 (in 0.89) |
| saw | 1.02 / 1.06 / 0.96 | 0.83 / 0.49 / 1.20 | 0.80 / 0.48 / 1.18 |
| noise | 1.00 | 1.39 (in 1.40) | 1.43 (in 1.40) |
| noise | 1.02 / 1.06 / 0.96 | 1.70 / 1.68 / 1.59 | **1.41 / 1.45 / 1.44** |

**On tonal material the two are indistinguishable** — within 0.03 dB at every ratio. The one
systematic difference is broadband: Rubber Band leaves the noise envelope essentially
untouched (+0.04 dB) where SoundTouch adds ~+0.25 dB. Small, but consistent across ratios.

**Two harness traps, both of which produced wrong answers first:**

1. **Do not compare envelopes on music.** Aligning output against input can only be done to
   the envelope-window granularity (10 ms), and at 10 ms a kick lands in the wrong window. The
   first version of this harness reported 1.4–6.1 dB of "artefact" for cases that are known to
   be transparent, so its engine-to-engine numbers were meaningless. **Corollary: the
   "2.6–5.3 dB of level modulation at 1.06×" recorded earlier in this log came from a
   different metric and cannot be reconciled with today's +0.25 dB on noise — treat that
   magnitude as unconfirmed.** The unity figure (1.42 dB, from the seek offsets read directly)
   is unaffected, because that one is ground truth rather than an envelope comparison.
2. **The Rubber Band kernel needs an explicit warm-up.** Its WASM instantiation is async and
   `process` silently writes nothing until it is up, so a whole case can come out as pure
   silence (it showed up as `NaN` and `peak 0.000`). Fix: repeat the first block until output
   appears, then run for real — valid because the test signals are stationary.

A quadrature-fit distortion metric was also tried and is **not** trustworthy here: it
conflates frequency error with distortion, and SoundTouch's 1.1-cent detune makes its fit
decohere over a 6.5 s window (it read −120 dB for Rubber Band vs −11 dB for SoundTouch, which
is the detune showing up, not 36 dB of real distortion). The AM metric above is the sound one.

**Recommendation: keep SoundTouch as the default.** Not because it sounds better — on tone it
is a tie — but because the quality difference in the only case that matters is ~0.2 dB of
envelope modulation, i.e. inaudible, while Rubber Band's costs are structural and measured:
its binding resets the stretcher on *every* ratio change, so a deck needs two kernels and,
during a fader sweep, the key sits ~7.7 cents out (median), where SoundTouch's pitch is an
AudioParam and ramps continuously — and a deck's rate changes ~20×/second from the sync PLL.
Rubber Band stays available via `setKeyLockEngine('rubberband')` as the escape hatch if
WSOLA's seek artefact ever turns up at a non-unity ratio on real material.

**Verified:** `tsc --noEmit` clean; `npm run build` clean; full `npm test` green.

## RB_KEYLOCK_LATENCY_SAMPLES is only right near a centred fader (measured, not assumed)

`measure-rb-latency-vs-ratio.mjs` (new). Correlation cannot measure away from unity — the peak
collapses to ~0.05 — so this uses a **step response**: silence lead, then a tone, delay read as
the 50%-of-steady crossing. Validated at unity against the correlation: 4101 vs 4096, the
+5-sample bias the method is known to have ((fs/f)/12).

| rate | pitch | samples | ms @48k |
|---|---|---|---|
| 0.90 | 1.111 | 3970 | 82.7 |
| 0.95 | 1.053 | 4113 | 85.7 |
| 1.00 | 1.000 | 4096 | 85.3 |
| 1.05 | 0.952 | 4369 | 91.0 |
| 1.08 | 0.926 | 4371 | 91.1 |
| 1.25 | 0.800 | 4770 | 99.4 |

Flat to a few ms at or below the deck's own tempo (where synced decks usually live), growing
once pitched up — up to **14 ms at 1.25x**. Per-frequency spread ±25 samples, so the effect is
real. It does not fit a simple law (not proportional to the ratio or its inverse), so the flat
constant was kept deliberately; the numbers are in the `RB_KEYLOCK_LATENCY_SAMPLES` doc comment.

**Where the error lands — the reason this matters.** `audiblePosition` subtracts the latency
from the deck whose wet path is live and nothing from a dry deck. Two keylocked decks or two
dry decks share the error and cancel it exactly; a **mixed** pair does not, so it shows up as
the keylocked deck sitting that many ms off. Consequence: if a keylocked deck sounds slightly
late against a dry one and it is pitched up, look here first. Note this does *not* explain the
reported "almost but not perfect" when the synced deck's rate is near 1 — there the constant is
correct — so that residual is still open.

### Harness notes (corrections to earlier recipes)

- A warm-up that repeats a **tone** until output appears is wrong for a step response: every
  block is queued as *input* and comes back out, so the burst drains straight into the measured
  region. Warm up on **silence**, prove liveness with a short burst, drain, then measure.
- Search for the crossing from `stepAt - 8192`, not from the top of the stream, or the burst
  drain triggers it.
- The step response is a **ramp** (OLA crossfades two windows; unity sums to unity for a
  *stationary* signal, hence the 0.998 correlation, but smears a transient). A floor-based
  onset therefore reads the ramp's shape, not the delay: at unity the floor-1e-7 reading was
  2828 and floor-1e-2 was 4097. Use the midpoint.
- `measure-keylock-latency.mjs`, `keylock-wobble.mjs`, `measure-latency-vs-tempo.mjs` and
  `compare-keylock-engines.mjs` now fail: they load `public/soundtouch-processor.js`, which was
  deleted with the engine. Obsolete, not broken. `measure-rb-latency.mjs` is still valid and
  re-confirmed 4096 samples at 44.1 and 48 kHz.

## AUTO now bass-swaps; default fade length 32 beats

User: *"set default crossfade beats to 32. it would be cool if we crossfade on auto-pilot, it also
auto adjusts the Low EQ …"* — `TraktorTransportBar.tsx` + `TraktorMixer.tsx`.

Default is now index 3 of `FADE_BEAT_STEPS` (32 beats = eight bars).

**The swap, as specified:** starting a fade cuts the incoming deck's Low to 9 o'clock straight
away and holds it there for the first half; at the midpoint the two cross over — the incoming one
rises to 12 o'clock while the outgoing falls to the same 9 o'clock, both across the second half.
Result: exactly one deck carries a full-depth low at every instant, and the incoming deck owns the
bass by the time the fader reaches the far end. Fading back reverses the roles exactly, because the
deck left holding the cut is the next one to be faded in.

**9 o'clock is −8 dB, and it is not a round number by luck.** The Knob sweeps 270°: `START_ANGLE
= −135°` (7:30) through 0° (12:00) to +135° (4:30), and the mixer's Low knob runs −12…+12 dB, so
the 135° negative half covers 12 dB and 9 o'clock (−90°) is exactly **−8 dB**. `BASS_SWAP_CUT_DB`
carries that derivation, since the constant is meaningless without the knob's range.

**The knob has to be able to move.** `TraktorMixer` kept the Low in local `useState` seeded at 0, so
an engine-side change would have moved the sound but not the knob — the autopilot would have been
invisible. Both LOW knobs now read `deck.eqLowGain`, and `Knob` is fully controlled (`const angle =
valueToAngle(value, …)`), so the engine drives the pointer. The other EQ bands still use local
state; only the band the autopilot touches was converted.

**Measured in the live page** (fresh tab, 4-beat fade for speed, Deck A fading in from 0):

| point | crossfader | Deck A Low | Deck B Low |
|---|---|---|---|
| at rest | 0 | 0 | 0 |
| first half (whole) | — | **−8** held | **0** untouched |
| midpoint | −0.51 | −7.85 | −0.15 |
| swap samples | −0.6…−0.95 | −6.85 → −0.73 | −1.15 → −7.27 |
| end | −1 | **0** (12:00) | **−8** (9:00) |

The two swapped values sum to exactly **−8 dB at every sample** — the hand-over keeps the total low

## White boxes at zoom: the mini waveform canvas sized itself from its own attributes

User: *"when we zoom in or out on the site it shows those unhappy faces in a white rectangle —
why? can u fix that?"*, followed by *"in Firefox this doesnt happen, only in Chrome and Edge"*.

The faces were the two **mini waveform canvases** in the deck headers — the only canvases in that
strip, one per deck. Chromium paints a canvas it has no usable surface for as an opaque white box
with a broken-content glyph; Firefox keeps whatever it last drew, so it never showed there. That
difference was the clue that it was a canvas-surface problem rather than anything we draw.

**The cause was a layout feedback loop, not a drawing bug.** `MiniWaveform`'s canvas was a flex item
(`h-full flex-1`) with no definite width. A canvas is a replaced element whose intrinsic size *is*
its `width`/`height` attributes, and a flex item's automatic minimum size is its intrinsic size —
so the backing store the draw loop sized from `rect.width * dpr` became the minimum width of the
element that was measuring `rect.width`. At any devicePixelRatio other than 1 that closes the loop:
the canvas grows by that ratio every frame until it passes Chromium's maximum canvas size, and past
that ceiling Chromium stops drawing and shows the placeholder box. At dpr 1 the loop is a fixed
point (`244 × 1 = 244`), which is why it only appeared once zoomed or on fractional display scaling.

Measured with a CDP probe (devtools `Runtime.evaluate`, `devicePixelRatio` overridden, canvas
`width`/`height` setters wrapped to count assignments) on `/mix-it` in headless Chromium:

| dpr | before | after |
|---|---|---|
| 1 | 1 resize/canvas, 244×22 CSS, 244×22 backing | unchanged |
| 1.1 | **60 resizes/s**, CSS width climbing 244 → 3293.6 → 14666.7 px, backing up to **16000×24** | 1 resize, 244×22 CSS, 268×24 backing, **0 resizes in a 3 s window** |
| 1.5 / 2 | same climb | 366×33 / 488×44 backing, CSS steady at 244×22 |

Two changes. The loop is cut by taking the canvas out of layout sizing: it now sits
`absolute inset-0` inside a `relative h-full min-w-0 flex-1` div, so its own backing store can no
longer feed back into the width it measures. The sizing comparison was also wrong on its own —
`canvas.width !== w * dpr` can never be equal when the product is fractional, since the assignment
truncates — so both canvases (this one and `StackedWaveforms`) now round the store to whole device
pixels and compare against that, and scale the transform by `bw / w` so CSS-pixel drawing fills the
store exactly. That also removed a half-pixel unpainted strip along the bottom edge at fractional
ratios (22 × 1.25 = 27.5, formerly 27, now 28). `StackedWaveforms`' `renderDeckLane` recovers its
lane width from `ctx.getTransform().a` instead of dividing by `devicePixelRatio`, which would now
disagree with the rounded store by up to half a pixel per lane coordinate.

**Verified** — the 60→1 resize counts above; `npm run typecheck` and `npm run build` both exit 0;
headless screenshots at dpr 1/1.1/1.5/2 show no white blob larger than a text glyph, and the dpr 1

## Glitchy playback: the output buffer, not the graph

Reported as audio glitches "esp. when I hit a button or fading is on autopilot", intermittent, with
the user's own suspicion being the buffer. It was the buffer. `AudioEngine` built its context with
`latencyHint: 'interactive'`, which on this machine's real WASAPI device (measured in a normal,
non-headless Chrome off-screen, 48 kHz, 16 cores) is a **10 ms / 480-frame** block, 40 ms output
latency. 10 ms is the entire tolerance the render thread has for being late, against a desktop audio
stack that routinely hiccups for longer — hence dropouts that correlate with *anything* else going on
rather than with a specific control.

What was ruled out first, so the buffer didn't get blamed by default:

- **The keylock voices are cheap.** Two high-quality Rubber Band kernels per deck (one audible, one
  spare, both fed continuously) looked like the obvious suspect, since a worklet's `process` runs on
  the audio render thread. Offline-rendered through the real `rubberband-processor.js`: 10 s of audio
  takes 0.098 s wall with **four** high-quality voices at pitch 1.05, i.e. ~100x realtime, under 1 % of
  a core each. Not the cause, and the primed-spare design costs nothing worth changing.
- **The main thread is not blocked.** A track playing for 8 s moved 120 mutations/s at a steady 60 fps
  with **0 long tasks** and 0 blocking ms; the AUTO crossfade scenario measured identically. So the
  position-emit storm (a deck notifies its listeners every 2 quanta, ~187 Hz, and ten components
  subscribe with `setVer(v => v + 1)`) is real but was not producing stalls here.
- Every parameter glide in the path is already smooth: crossfader and channel faders, EQ, trim, FX
  sends and the keylock wet/dry swap all use `setTargetAtTime`.

The fix is `src/lib/dj/audio-latency.ts`: 30 ms (1440 frames, 64 ms output) by default, with
`keybpm:audio-latency` in localStorage taking a level (`tight` 10 ms / `balanced` 30 ms / `safe`
60 ms) or a number of seconds, clamped to 0.01–0.2. Read once at context construction, so a change
needs a page load; `AudioEngine.bufferLatencyMs` reports what the device actually granted.

**Verified** by hooking `window.AudioContext` before app code and loading `/mix-it` in headless
Chrome: no preference → `hint 0.03`, `baseLatency` **30 ms** (was 10 ms); `'safe'` → 60 ms; `'0.05'`
→ 50 ms; `'nonsense'` → back to 30 ms; `'0.9'` → clamped to 0.2 (Chrome then grants 170 ms, so it caps
the buffer itself well below 200). Real-device numbers for the record: `playback` 20 ms base / 48 ms
output, 0.03 → 30 / 64, 0.06 → 60 / 88. `npm run build` (tsc -b + vite build) exit 0, and a playback
smoke test through the dev server still loads, plays, and holds 60 fps.

Not fixed, and worth knowing: a hard position jump (`seek`, hot cue, the bar-align inside sync) still
moves the worklet's read head in one sample, so it steps the waveform — a click, not a dropout, and a
different complaint from this one. A declick (fade out, jump, fade in across the next block) is the
obvious follow-up if the user hears clicks on cue presses specifically.

## MOVE now travels the loop along bar lines

MOVE used to shift the loop by exactly its own length, which is musically arbitrary: a loop that
started off a downbeat stayed off a downbeat, and a two-beat loop landed mid-bar every time. It now
lands on **bar lines**, always at least one loop length away in the direction pressed.

The rule lives in `src/lib/dj/loop-move.ts` as a pure function (`loopMoveDestination(loop, grid,
direction, duration)`), which `DeckEngine.loopMoveTarget` wraps so the transport still asks the deck;
the component's helper is now a one-line delegation and the arrows' disabled state is the same call,
null meaning "nowhere to go". Two decisions in the rule are worth the ink:

- **Bar lines, not "round the length to bars".** Bar lines because a loop that travels by its own size
  alone drifts off the phrase; and the loop **keeps its own length** rather than being resized, so a
  two-beat loop stays two beats but moves a whole bar — which is the only whole-bar step it has.
- **"At least one length", not "nearest bar line".** A loop need not start on a bar line (SNAP off, or
  dragged in). Nearest-bar snapping would move such a loop *backwards* while the forward arrow was
  pressed; taking the first line at or past the reach always moves forwards, and the first press also
  squares the loop up onto the grid. `BAR_EPSILON` exists because a bar line that lands exactly on the
  reach is one length away and allowed, and the beat times are floats.
- The grid parameter is **required**, not optional: letting the lookup fall back to `grid.ts`'s 120 BPM
  default would snap a 174 BPM unanalysed track's loops to 120 BPM bar lines. `loopMoveTarget` gives
  such a track a constant grid at its own tempo instead — deliberately *not* `ensureGrid()`, which
  would materialise a grid on the track and so make every bar-stripe display start drawing the first
  time MOVE was pressed.

**Verified** by `scripts/test-loop-move.mjs` (wired into `npm test` after the grid tests): 63 checks
on a constant grid (128 BPM, bar anchor 2.0 s), a hand-built **variable** grid whose destination has
to be one of *its* bar times, and a constant grid at 174 BPM standing in for an unanalysed track —
bar-aligned forward and back, sub-bar loops moving a bar, off-grid loops squaring up without moving
backwards, length preserved across six repeated presses each way, and refusal at the first bar line
and past the end of the track. Two of the checks are deliberate negative controls (`|destination -
plain shift| > 1e-6`), so the suite fails if the bar snapping is ever removed. Two of my own
expectations were wrong when first written — the grid's first bar line is at 2.0 s, not 0, and six
presses from bar 0 land on bar 6 — and the test caught both, which is the point of asserting exact
bar times rather than "moved by more than X". `npm test` exit 0 (including the beat bench gate),
`npx tsc -b` exit 0, `npm run build` exit 0. In the app, the headless probe still shows the same
sequence as before the rule changed — arm, `>` doubles 4 → 8 in LOOP, MOVE disables the middle, `>`
flips the left arrow from disabled to enabled and `<` flips it back — with no render errors from the
engine call in that path.

Not verified: that the drawn loop band visibly sits on a drawn downbeat stripe. Reading the lane
canvas failed once already for the same reason as before (the waveform envelope is painted over the
loop highlight), so this rests on the unit-tested geometry plus the lane's existing bar drawing.

## Loop cluster: press feedback on the `<` / `>` chevrons

User wanted the same outline they see on the − / + under the pitch fader when the LOOP/MOVE
chevrons (in `TraktorTransportBar.tsx`) are clicked.

**Where the reference lives:** in `MixIt`, the − / + under the pitch fader are `TraktorDeck`'s tempo
step buttons, and their feedback is `active:border-white active:text-white` on a bordered rounded
box — the outline exists only while the button is held.

**Change:** one shared `CHEVRON_PRESS` const applied to both chevrons:

```
active:border active:border-white active:bg-[#2b2b2b] active:text-white active:transition-none
```

**Why the cell's own border, not a ring:** the first cut used an inset ring
(`active:ring-1 active:ring-inset active:ring-white`). It worked, but the user pointed out (with a magnified screenshot) that the ring
is *not* the button's outline — it sits 1px inside the seam the cell already draws, so the seam and
the ring read as two lines and the framed cell looks like a box drawn inside the button. Using the
border instead is both closer to the pitch fader reference (which is `active:border-white` on a
bordered box) and structurally honest: `active:border` gives the three sides that have no width at
rest their 1px and `active:border-white` recolours the seam, so all four edges join up on the
cell's own border box with nothing painted inside it. Nothing moves, because the cell is `w-6`
under border-box sizing — the new edges eat into padding, not width, and the glyph stays centred.
**`active:transition-none` is load-bearing.** Adding the border uncovered a real bug that the ring
had hidden: the cell's `transition-colors` covers border-color, background-color and color, so the
outline *faded in* over Tailwind's 150 ms default — longer than a click, meaning a quick tap never
reached full white. (The ring looked instant only because box-shadow is not in `transition-colors`.)
Killing the transition while the button is down makes the white appear in the same frame as
mousedown, and the release still fades out.

**Trap for next time:** `getComputedStyle` returns the *animating* value, so a just-added class
reads as the old colour until the transition finishes. That is what first looked like "the rules
don't apply" — the same read on a probe element without `transition-colors` returned white
immediately, which is what pointed at the transition rather than at specificity.

**Verified:** `npm run build` (`tsc -b && vite build`) exit 0, and the emitted stylesheet contains
`.active\:border:active{border-width:1px}`, `.active\:border-white:active{… rgb(255 255 255 …)}`,
`.active\:bg-\[\#2b2b2b\]:active{…}`, `.active\:text-white:active{…}` and
`.active\:transition-none:active{transition-property:none}` — with the old `ring-*` utilities now
absent from the CSS, so nothing still uses the previous approach. On the running dev server, all
four chevrons carry the five classes and the resting computed style is untouched (only the seam
border, transparent background, `#666666` glyph). Pressing was replayed by cloning the real
`:active` rules out of the live CSSOM into a `.sim-press` class, which showed: instantly (no fade)
all four borders 1px white, background rgb(43 43 43), glyph white, `box-shadow: none`; and — the
check that matters for this change — the cell's rect identical to rest (`216.25 → 240.25`), its
right edge exactly equal to the middle cell's left edge, so the outline shares the seam instead of
sitting inside it.

**Caveat:** the preview tooling has no hold-a-button primitive (Playwright's click is down+up inside
one frame), so the pressed state was reproduced by replaying the stylesheet's own declarations
rather than by physically holding the button. The final magnified screenshot of the border version
could not be taken either — the preview webview stopped compositing frames mid-session and kept
refusing, so that last look is on the user's own copy of the running preview.
