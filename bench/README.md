# Beat-grid benchmark

`npm run bench:beats` scores the analyzer against known beat times and known bar
lines — and can score a different analyzer on the same audio, same metrics, same
table, which is how "should we use Beat This!" gets answered ([Scoring another
analyzer](#scoring-another-analyzer)) — using the metrics in
[src/lib/dj/beat-metrics.ts](../src/lib/dj/beat-metrics.ts):
F-measure at 70 ms (mir_eval's `beat.f_measure` tolerance), continuity (CMLt/AMLt),
grid drift, and — for the bar — a downbeat match rate, the whole-beat offset of
the bar lattice, and drop markers against annotated section changes. It runs in
CI, in Node, with no browser and no downloads.

```
$ npm run bench:beats

trap-halftime-140             0.994   1.000   0.988   1.000   1.000  140.0/140.0   const   measurement  0 dec  0/0              match 99% mean 1ms p95 2ms late 2ms drift 0.0ms/min
midbar-intro-124              1.000   1.000   1.000   1.000   1.000  124.0/124.0   const   measurement  0 dec  0/0              match 100% mean 1ms p95 1ms late 1ms drift -0.0ms/min
breakdown-bass-126            0.995   1.000   0.989   0.989   0.989  126.0/126.0   const   measurement  0 dec  1/1              match 99% mean 5ms p95 5ms late -5ms drift 0.0ms/min
…
aggregate: mean F 0.993   median CMLt 1.000   median AMLt 1.000   mean |err| 6ms   worst |drift| 134ms/min   variable grids 3/11   octave errors 0   downbeats 0.997   bar errors 0 (wrong claims 0, missed 0)   drops 0 missed / 0 extra   3766ms total
```

The `bar` column reads: whole-beat offset of the bar lattice from the annotated
downbeats (`0` is correct, `-1` is bar lines a beat early), whether the analyzer
*claimed* a rotation (`dec`) or kept the anchor and said so (`amb`), and how many
annotated drops it found over how many were annotated.

What it measures is the **stored grid**, read back through the same accessors the
deck uses (`beatIndexAt` / `beatTimeAt` / `barTimeAt`), not the tracker's internal
ticks — so a change that improves the tracker but not the grid the DJ sees cannot
pass.

## Two corpora, two different jobs

**Synthetic (default, what CI runs).** Eleven deterministic tracks generated by
[scripts/lib/beat-corpus.mjs](../scripts/lib/beat-corpus.mjs), each with an exact
annotation because the annotation *is* the schedule the synthesizer played:
steady house, offbeat-bass techno, drum and bass, a wobbling live drummer, an
accelerating track, humanised jitter, a pad intro with a kick drop, claps and hats
with no kick at all, a half-time trap pattern, an intro that starts on the fourth
beat of a bar (a pickup), and a breakdown with a drop. They gate regressions. They
are **not** an accuracy claim: click-accurate synthetic audio has none of the
ambiguity real music does, so a score here can look better than the analyzer
really is.

Each case also carries **bar ground truth**: `rotation` (how many beats after the
first audible beat the true downbeat sits), `downbeats`, `drops`, and
`rotationDecidable` — whether the audio's kick, bass or snare pattern actually
states the bar. That last flag is what makes the bar gates meaningful in both
directions: material *with* a recoverable downbeat must be decided, and material
*without* one must not be guessed at. A four-on-the-floor kick with no bass note
and a snare pair on 2 and 4 is genuinely undecidable — the snare pair fits two
rotations, and the pair is the same whichever way the bar is read — so the analyzer
reports the candidates it could not rule out and keeps the first audible beat as
bar 1. That is scored as a pass; claiming one of the two would be the defect.

**Annotated (opt-in, `--corpus DIR`).** The only mode that can support an accuracy
claim. Layout, either shape:

```
corpus/
  name.wav + name.beats              # flat
  audio/name.wav + annotations/name.beats   # Ballroom / SMC style
```

`.beats` files are one time in seconds per line (comments and the two-column
`time beat` variant are tolerated). A two-column file **is** a bar annotation: the
second column is the beat's number inside its bar, `1` on the downbeat, so GTZAN
and the Beat This! annotation set get their bar scored without a separate
`.downbeats` file. Where to get them (audio must be downloaded separately; none of
it is in this repo):

- **Ballroom** — 698 ballroom dance tracks with beat and downbeat annotations.
- **SMC MIR** — 217 tracks, beat and downbeat.
- **Harmonix Set** — 912 tracks, beats and downbeats, many electronic.
- **GTZAN-beats**, **RWC** — also widely used for beat tracking.

```
npm run bench:beats:corpus     # expects bench/corpus/, writes bench/last-run.json
```

The JSON report is intended for trend tracking: keep it as a CI artifact and the
question "did this change help?" stops being an opinion.

## Scoring another analyzer

The analyzer above is not the only candidate. `--trackers DIR` puts an outside beat
tracker in the same table, scored by the same metrics, so "is this one better on
real music" is a measurement rather than an opinion:

```
$ python bench/trackers/run_trackers.py --corpus bench/corpus      # where the trackers run
$ node scripts/bench-beats.mjs --corpus bench/corpus --trackers bench/trackers/out --no-gate
```

The Python runner writes one MIR-standard `.beats` file per track per tracker
(`<out>/<tracker>/<track>.beats`: `time`, then a beat number where `1` is the
downbeat — the format the corpora ship and the one Beat This! writes). The Node
side reads that cache, turns the beat times into the grid a DJ would get, and
scores it with `beat-metrics.ts` like any other grid. External trackers are
reported, never gated: the gates are regression floors for code we own.

Three things to know about how the comparison is set up:

- **No hint BPM, and no fitting.** The tracker's own beats are stored verbatim as
a variable-tempo map. Fitting a single tempo over them would erase the exact
difference we want to see — a tracker that follows a drifting track and one that
does not would score the same.
- **The bar is only scored when the tracker claims one.** librosa writes one
column and has no downbeat concept, so its bar column reads `—`; its `first beat
is beat 1` is not a phase error, it is an absence of evidence. A two-column file
is a claim, and it is scored like our analyzer's (`ext` in the claim column, so a
model's claim is not mistaken for ours).
- **Speed is part of the answer.** The runner records seconds per track in
`timings.json` and the report prints the total, because a model that is a point
better and twenty times slower is a different decision for an app that analyses
in a browser.

Which trackers are wired up: `beat_this` (CPJKU Beat This!, MIT, transformer on
log-mel, beats + downbeats, `final0` checkpoint), `librosa-beat`
(`librosa.beat.beat_track`, global tempo, beats only) and `librosa-plp`
(framewise pulse, beats only). Adding one is a function in
[run_trackers.py](trackers/run_trackers.py) plus a `TRACKERS` entry.

```
python -m venv bench/.venv
bench/.venv/Scripts/python.exe -m pip install -r bench/trackers/requirements.txt   # Windows
bench/.venv/bin/python -m pip install -r bench/trackers/requirements.txt           # macOS/Linux
```

Beat This! pulls in torch and torchaudio (the bulk of the install) and downloads
its checkpoint (~78 MB) on first run; everything is cached outside this
repository.

### The leakage rule

The published Beat This! checkpoints (`final0`, `final1`, `small*`) were trained
on all of the project's data **except GTZAN**. Scoring them on Ballroom, SMC or
Harmonix is measuring memorisation, not tracking — those are that model's
training set. Two honest options:

- **GTZAN** (`npm run bench:corpus:gtzan`), the authors' held-out set. It fetches
the annotations from CPJKU's `beat_this_annotations`; the audio is no longer
distributed by GTZAN's authors, so `--audio DIR` points at a copy you have and
the script links it into `bench/corpus/gtzan/` next to the annotations.
- **A `fold*` checkpoint** on its own held-out fold, for any of the other
corpora. `--model fold0` on the corpus's fold-0 test split is a fair number;
`--model final0` on all of it is not.

### The synthetic corpus is a smoke test, not a comparison

The repository cannot ship real music, so `--emit DIR` writes the synthetic
corpus to disk as WAV + annotations and the whole chain can be exercised without
a download:

```
npm run bench:beats:emit
python bench/trackers/run_trackers.py --corpus bench/corpus/synthetic
npm run bench:beats:trackers
```

Those numbers say the wiring works. They say almost nothing about real music:
click-accurate synthetic tracks are out of distribution for a model trained on
recordings, which is why Beat This! reads a half-time reading on the trap case and
loses the phase on the jittered one there. An accuracy claim needs annotated real
audio.

## Gates

The synthetic corpus runs with gates (`GATES` and `PRIMARY_GATES` in
[scripts/bench-beats.mjs](../scripts/bench-beats.mjs)). Measurement path: mean F
≥ 0.97, median CMLt ≥ 0.97, mean absolute error ≤ 20 ms, worst per-track drift
trend ≤ 150 ms/min, downbeat match ≥ 0.97. Primary path: the same shape one notch
looser (0.95 / 0.95 / 40 ms / 150 ms/min / 0.95), because its front end is a WASM
kernel we do not control while its decision layer is ours. They are *regression
floors* with a margin under the current readings (0.993 / 1.000 / 5–6 ms /
134 ms/min / 0.997), not targets and not claims. A change that needs a floor
lowered is a change that made the analyzer worse; that should be argued in the
commit message, not quietly accommodated.

The bar has four gates of its own, and they are the reason downbeats are scored at
all — a whole-beat bar error is invisible to the beat metrics and ruins a mix:

- **no track whose bar lines are a whole beat out**,
- **no rotation claimed that is wrong** (a wrong claim is worse than no claim,
  because the DJ has no reason to check it),
- **no decidable rotation left undecided** (the corpus says which are decidable),
- **no annotated drop missed, and no drop invented** — a spurious marker sends a
  mix looking for a change that is not there.

## What the benchmark already caught

The first run scored mean F **0.772** and immediately exposed four defects that the
synthetic unit suites could not see, all since fixed:

| Track | Before | Cause | After |
|---|---|---|---|
| `techno-138-offbeat-bass` | F 0.000, 205 ms phase error | the phase anchor scored the kick group alone, so it locked the grid to a sub-bass on the offbeat | F 1.000, 0 ms |
| `dnb-174-break` | 86.9 BPM for a 174 BPM track | the 85/185 BPM threshold does not fire at 86.9, so nothing doubled it | 175.2 BPM in a beat map, F 0.976 |
| `live-drums-96-wobble` | F 0.583 | the measurement path never built a beat map, so a wobbling track kept a rigid lattice | F 0.992 |
| `rising-tempo-124-128` | F 0.709, 106 ms late | same, plus no tempo refinement | F 0.994, 2 ms |
| every steady track | 25–30 ms early | the frame→time convention put onsets at the window centre; a transient actually enters the window late | ≤15 ms |

## What the benchmark caught in the primary path

Scoring the path the application actually runs took one change: the Essentia WASM
kernel loads in Node as well as in the browser, so `analyzeBeatGrid` — the primary
path — can be measured headlessly too. It was **worse than its own fallback**:
mean F **0.626** against the measurement path's 0.992.

| Track | Before | Cause | After |
|---|---|---|---|
| `dnb-174-break` | 87.0 BPM stored for a 174 BPM track (F 0.662) | the primary path decided the octave with an ad-hoc pairwise cross-check, and marked Essentia's tactus as a *committed* vote, which froze the choice before the tempo prior could tie-break | 175.2 BPM, F 0.976 |
| `humanised-122-tight`, `pad-intro-kick-drop-126`, `trap-halftime-140` | F 0.000, 211–240 ms phase error | the phase came from Essentia's tick list, whose accents sat half a beat off the beat; it now comes from the same evidence envelope the measurement path uses | F 0.993 / 0.992 / 0.994 |
| `trap-halftime-140` (after the phase fix) | still 213 ms out | both paths now measure the *loudest rhythmic window*, not the intro — the intro's hats put the anchor half a beat off | 1 ms |

Both paths now read the same numbers on this corpus, which is the point: the
primary path is the measurement path plus Essentia's vote, not a second analyzer
with its own opinions. Neither is an accuracy claim — see below.

## What the benchmark caught in the bar structure

Scoring downbeats was new, and it found defects on the first run — in the anchor,
and in the metrics themselves:

| Track | Before | Cause | After |
|---|---|---|---|
| `live-drums-96-wobble`, `rising-tempo-124-128` | bar 1 three beats late, every bar line a beat out | the first-beat anchor looked for the first lattice beat whose ±35 ms window held a kick. On jittery (±3 %) or accelerating material the beats wander 56 ms by the fourth beat, the kicks fell outside their windows, and the scan walked forward until a lattice point happened to line up | the first *onset* is read from the envelope and snapped to the lattice, so a late onset still names its own beat: bar 1 at 0:00 |
| every steady track | a spurious `intro` drop at bar 1 | the preamble it measures started at bar 1 inclusive, so 5 ms of the first kick was enough to make silence look like a *x3.4 energy arrival* | the preamble stops a quarter of a beat before bar 1 and is suppressed when a beat before the bar already carries a kick |
| every track, both ends | the first and last downbeats never matched | the downbeat list was requested over the exact annotated span, and a bar line 4 ms outside it was dropped instead of matched | the report asks for a tolerance of slack at both ends |
| the whole bar column | every track read `offset 0` | the metric's "nearest annotated downbeat" search compared against itself, so it always returned the grid's own anchor | initialised properly; this is what exposed the anchor defect above |

## What is still not scored

Real music — because no real annotated corpus is in this repository, and inventing
one would be the synthetic corpus in a different costume. `npm run bench:corpus:gtzan`
now fetches the annotations and lays out the directory; the audio still has to come
from a copy you already have, since GTZAN's authors no longer distribute it. Two
facts about that corpus worth knowing before reading a number off it:

- **GTZAN clips are 30 seconds.** Long enough to score phase, downbeat and bar
  rotation — the first-downbeat complaint this benchmark exists to answer — but
  short for drift. Ballroom or Harmonix with a `fold*` checkpoint are the long-form
  check, and they ship downbeats.
- **It is one corpus.** Ten genres of 20th-century popular music is not a DJ
  library. A number that reads well there is evidence, not a conclusion, and the
  tracks you actually mix are the set that matters — a hand-checked export of them
  is the most useful corpus of all.

When a real corpus does carry bar ground truth the same columns apply; the bar
gates stay off for it, because the gates are regression floors for code we own and
these floors were measured on the synthetic set.

What the bar gates cannot cover is the ambiguous case: with no recoverable cue the
analyzer keeps the anchor, and if the anchor's beat happens not to be a downbeat
nothing here would notice. The stored `rotationDecided: false` and the candidate
list are the honest record of that, and the UI shows no phrase lines for a track
whose phrase length was never measured.
